# LightNote V0.8 后续改进路线评审

评审日期：2026-09-19

## 实施状态

- **V0.9：已实现并通过专项测试。** 已加入 0006 迁移、持久 tombstone、单调同步修订、服务端同步游标、附件原子校验和可验证原子备份恢复。
- **V0.10：已实现代码与自动化基线。** 已加入分页/虚拟化、连续分页测试、CI、发布前置检查和统一版本来源；超大数据连续试用仍属于人工发布验收。
- **V1.0：已实现主要日常使用项。** 标签与主要图片来源可保真导入，新增数据安全中心和脱敏诊断包，补充顶部核心操作的辅助功能名称；真实双设备与干净机器安装仍需外部环境验收。

## 结论

LightNote 已经跨过“功能原型”阶段：本地编辑、SQLite、全文搜索、附件、历史、备份、导入、安装包和 Firebase 同步的主链路均已建立，Release 配置下现有 31 个测试全部通过。后续最有价值的工作不是继续横向堆功能，而是先把真实数据长期使用会触发的同步、恢复、规模化和维护性问题收口，再定义 V1.0。

推荐顺序：

1. **V0.9 数据可靠性版**：修复删除同步、同步游标、附件校验和备份原子性。
2. **V0.10 规模与工程化版**：分页、模块拆分、自动化发布与故障注入测试。
3. **V1.0 日常使用版**：完善迁移保真度、冲突/恢复体验、可访问性与诊断能力。
4. V1.0 稳定后，再根据真实用户数据选择 Markdown、PDF/文件附件、WebDAV、多端或端到端加密；暂不建议优先投入 AI、协作或知识图谱。

## 当前基线

- 源码规模约 7,493 行：Core 257 行、Infrastructure 3,987 行、App 2,969 行、编辑器 280 行。
- 三个文件已成为明显的复杂度热点：`FirebaseSyncService.cs` 约 44 KB、`MainWindow.xaml.cs` 约 41 KB、`NoteImportService.cs` 约 36 KB。
- Release 测试：Core 2/2、Integration 29/29 通过。
- 覆盖率采样：集成测试覆盖约 61.1% 行、49.3% 分支；Core 独立测试约 17.5% 行。两个 `UnitTest1.cs` 仍是无断言占位测试。
- 没有发现 CI 工作流；版本号同时出现在应用项目、README、构建脚本和安装脚本默认值中。

## P0：V0.9 数据可靠性版

### 1. 建立不会丢失的同步 tombstone 与单调变更序号

**问题**

- 附件软删除 24 小时后会直接删除数据库记录；如果期间一直离线，待同步 outbox 随后只能发现实体不存在，并直接当作完成，远端删除不会发生。
- 笔记“永久删除”会同时删掉笔记和对应 outbox；若软删除尚未成功上传，其他设备仍保留旧笔记。
- 笔记本与附件的 outbox `local_version` 固定为 1；标签修改不增加笔记版本。同步进行中再次修改时，完成旧请求可能误删新变更。

**证据**

- `AttachmentService.PurgeExpiredAsync` 先删除附件行：`src/LightNote.Infrastructure/Storage/AttachmentService.cs:234`。
- `SqliteNoteRepository.DeletePermanentlyAsync` 删除 note outbox 与笔记：`src/LightNote.Infrastructure/Storage/SqliteNoteRepository.cs:221`。
- `PushOutboxAsync` 对找不到实体的项目调用 `CompleteOutboxAsync`：`src/LightNote.Infrastructure/Sync/FirebaseSyncService.cs:178`。
- 笔记本 outbox 版本固定为 1：`src/LightNote.Infrastructure/Storage/SqliteNotebookRepository.cs:65`。

**建议实现**

- 新增 `change_sequence` 或每实体单调 `revision`，任何正文、标签、附件引用、笔记本变更都递增。
- outbox 保存不可变操作快照，或至少保存 revision 与操作类型；完成时只确认同一 revision。
- 删除使用持久 tombstone；只有远端确认后才能清理本地 tombstone/文件。永久删除应表示“用户界面不可见”，不等于立刻抹掉同步证据。
- 为 tombstone 设计保留期与手动“彻底清理已同步删除数据”策略。

**验收**

- 离线 30 天后再同步，删除仍能传播。
- 同步上传过程中修改标签、笔记本或附件引用，不丢最后一次修改。
- 连续删除、恢复、再删除在两台设备上最终一致。

### 2. 用服务端游标替代客户端时间水位

**问题**

当前同步先记录本机 `syncStartedAt`，按远端文档的客户端 `updatedAt > lastPull` 拉取，完成后把本机开始时间写成新水位。设备时钟偏差、同步期间写入、相同时间戳或旧设备慢时钟都可能让更新永久落在水位之前。

**证据**

- 同步水位取本机时间并在结束时写回：`src/LightNote.Infrastructure/Sync/FirebaseSyncService.cs:102`、`:129`。
- 查询条件为 `updatedAt GREATER_THAN lastPull`：同文件 `:230`。

**建议实现**

- 优先使用 Firestore 服务端 `updateTime`、服务端时间戳或单调变更日志作为游标。
- 游标至少由 `(serverUpdateTime, documentId)` 组成，解决同时间戳排序；按页拉取并在每页成功提交后推进。
- 若短期仍保留客户端时间，应加入重叠窗口并依靠幂等去重，不能用本机当前时间直接跨越未观察区间。

**验收**

- 两台设备分别设置为快/慢 10 分钟，互相修改仍不漏同步。
- 同一时间戳的多条记录、同步中途新增记录、分页边界均完整拉取。
- 任一页下载或落库失败后重试，不跳过后续记录。

### 3. 附件下载必须原子写入并校验内容

**问题**

同步下载现在直接 `CreateNew` 写目标文件，随后把数据库状态标为 clean；没有校验远端字节数或 SHA-256。取消、磁盘满、代理异常或内容损坏可能留下不完整文件，并阻止下次重新下载。

**证据**

- 直接向最终路径复制：`src/LightNote.Infrastructure/Sync/FirebaseSyncService.cs:582`。
- 远端记录已带 `size` 与 `sha256`，但下载后未验证：同文件 `:611`。

**建议实现**

- 下载到同目录临时文件，流式计算 SHA-256，同时校验长度。
- 校验成功后原子改名，再在同一逻辑单元中更新数据库；失败时删除临时文件且保留待重试状态。
- 启动完整性检查增加“大小/哈希不匹配”与可选自动修复。

**验收**

- 模拟半包、错误哈希、磁盘写入异常与取消，最终路径不留下坏文件。
- 已损坏的本地附件能被识别并从云端重新获取。

### 4. 备份与恢复改为可验证、可回滚流程

**问题**

备份 ZIP 直接写最终文件名，失败或取消可能留下损坏文件；自动备份又按创建时间判断 24 小时内是否已有备份。恢复直接写用户目标目录，直到最后才检查数据库是否存在，没有先验证 manifest、数据库完整性或各文件哈希。

**证据**

- 最终 ZIP 使用 `FileMode.CreateNew` 直接创建：`src/LightNote.Infrastructure/Storage/BackupService.cs:42`。
- 恢复逐项写目标并在末尾只检查 `lightnote.db`：同文件 `:98`。

**建议实现**

- 备份先写 `.tmp`，manifest 写入格式版本、应用版本、数据库/附件大小与 SHA-256；关闭 ZIP 后自检，再原子改名。
- 恢复先解压到临时 staging 目录，限制总解压大小和条目数，验证 manifest、哈希与 SQLite `quick_check`，全部通过后再移动到目标。
- 自动备份只把“验证成功”的归档计入保留与 24 小时判断。

**验收**

- 备份中途取消、磁盘满、损坏 ZIP、缺失附件、未来格式版本均给出可恢复错误，不留下貌似成功的归档或半恢复目录。

## P1：V0.10 规模与工程化版

### 5. 为列表和搜索增加 keyset 分页与虚拟化

**问题**

仓储默认只返回 50 条，搜索最多 100 条，界面没有“加载更多”或分页状态。“全部笔记”在超过 50 篇后并不是真的全部；5,000 篇性能验收只覆盖搜索命中，不覆盖浏览体验。

**证据**

- `INoteRepository` 的列表默认限制为 50、搜索为 100：`src/LightNote.Core/Abstractions/INoteRepository.cs:9`。
- `MainViewModel` 调用时没有传游标或更高 limit：`src/LightNote.App/MainViewModel.cs:578`。

**建议实现**

- 仓储返回 `Page<T>` 与稳定 cursor，按 `(is_pinned, updated_at, id)` 做 keyset 分页，避免大 offset。
- UI 使用虚拟化列表、滚动加载和明确的总数/已加载数；切换筛选和搜索时取消旧页请求。
- 搜索结果也分页，并保留 bm25 排序的稳定次级键。

**验收**

- 5,000～50,000 篇数据下可以浏览到任意记录；首屏、下一页和搜索延迟都有基准测试。

### 6. 拆分三个复杂度热点，但暂不新增程序集

**建议边界**

- `MainWindow.xaml.cs`：拆出 `EditorBridge`、`WindowLifetimeCoordinator`、`SyncUiCoordinator`、导入/导出对话流程；尽量用命令替代 Click 事件。
- `FirebaseSyncService.cs`：拆出 Auth client、Firestore client、Storage client、sync planner、local sync store 和 conflict policy。
- `NoteImportService.cs`：每种格式一个 importer，共享规范化模型 `ImportedNote`；解析与落库分离。

这样可让错误处理和并发策略可单测，同时保持现有 Core/App/Infrastructure 三项目结构，不急于过度拆程序集。

**验收**

- 关键类控制在单一职责范围；同步协议、导入解析和 UI 生命周期可以不启动 WPF 即测试。

### 7. 建立可重复的 CI 与单一版本来源

**建议实现**

- CI 至少执行 `npm ci && npm run build`、`dotnet restore/build/test`、覆盖率阈值、发布产物检查。
- 构建脚本必须先重建 editor、运行测试，再 publish；安装烟雾测试作为发布候选阶段。
- 版本号集中到 `Directory.Build.props` 或版本文件，由 csproj、安装器、README/发布说明读取；避免 0.8.0 多处手工同步。
- 删除两个无断言占位测试，增加迁移夹具（每个已发布 schema 一份真实旧库）。

**验收**

- 任一提交可在干净环境重现安装包；版本号与内嵌编辑器资产不会错配。

### 8. 增加故障注入和并发测试，而不只追求覆盖率数字

重点场景：

- 同步请求进行中再次编辑；上传成功但本地确认失败；拉取一半失败；重复/乱序远端记录。
- SQLite busy、磁盘满、只读目录、备份取消、恢复损坏归档。
- WebView2 尚未 ready、快速切换笔记、图片上传回调晚到旧笔记。
- 数据库 0001～最新迁移的逐版本升级与失败回滚。

建议把行覆盖率作为底线，但以关键状态机的场景矩阵作为发布门槛。

## P2：V1.0 日常使用版

### 9. 提升导入保真度

当前 ENEX、Keep、CSV 标签被追加到正文，不会进入现有标签表；ENEX/Keep/Markdown/HTML 图片也只留占位。建议先统一 `ImportedNote` 模型（正文、标签、附件、来源 ID、时间、置顶），再由一个事务化 writer 落库。

优先顺序：

1. 标签真正写入 `tags/note_tags`。
2. Markdown/HTML 相对本地图片复制并去重。
3. ENEX 资源按 hash 与 MIME 还原。
4. Keep Takeout 附件与整个 ZIP 导入。
5. 导入前预览、重复检测、失败后可撤销本批导入。

### 10. 把冲突、恢复和同步状态做成用户可理解的“数据安全中心”

- 展示待同步数量、最后成功时间、最近错误、冲突版本和缺失附件。
- 冲突历史支持并排预览、选择保留或复制为新笔记。
- 备份支持“验证”“浏览内容”“恢复为新资料库”，并明确当前恢复功能不会原地覆盖运行中的数据库。
- 提供一键生成脱敏诊断包（版本、日志、迁移状态、完整性结果，不含正文和 token）。

### 11. 可访问性与国际化

现有快捷键和部分 AutomationProperties 已有基础，但大量按钮仍靠可见文本/ToolTip 与 code-behind Click。建议补充：

- 所有图标/格式按钮的 Automation Name、键盘焦点顺序和屏幕阅读器状态。
- 200%/300% 缩放、窄窗口、高对比度、键盘全流程验收。
- 将中文字符串移入资源文件，为错误信息、日期和复数建立可本地化边界。

## 暂缓项

以下方向有价值，但在 P0/P1 完成前会放大维护和数据模型压力：Android/PWA、WebDAV/Google Drive、端到端加密、任意文件附件、OCR、AI、协作、手写与自由画布。建议以真实用户反馈、导入来源分布和同步故障数据决定先后，而不是同时开线。
